# B5, the corrected rerun — quegee, 2026-09-22

What produced these files, so a reader can tell what they are evidence of.

## Why there is a B5

An attribution run on the measuring host, outside this harness, found two
things behind B4's WCC and BFS rows:

- **An allocator artifact, and it was the harness's.** B4's Grust participant
  called `prepare_incoming()` inside the build timer for every algorithm, to
  make its build column the same work as grustcat's constructor. WCC and BFS
  read no in-arcs, so for those two the harness built and freed a transpose
  nothing would read immediately before the call it timed. Freeing a large
  mapped chunk raises glibc's own mmap threshold, and the first call after it
  took about 112 to 128 more minor page faults. B4's `grust-next` first calls
  were slower and its second calls faster than the code alone accounts for.
- **A real regression, since fixed.** `WorkMeter::charge` had been pushed out
  of line in 16 kernels at `4d8e5db`, which is what B4 timed. It is inlined
  again at `ca68900`, the commit timed here, which also adds child contexts and
  `with_execution`.

B5 corrects the harness for the first, times the second, and records the page
faults beside every call so that neither has to be taken on trust again.

## What changed in the harness since B4

- `--prepare-incoming needed` is the default: the transpose is built inside the
  build timer only for PageRank's pull kernel, the only kernel in this matrix
  that reads in-arcs. B4's behaviour is `--prepare-incoming always`, the
  `+eager` variant, timed as its own row at the protocol sizes.
- Every participant reports the minor page faults of the call it times, read
  outside the timer with `getrusage(RUSAGE_SELF)`: the Grust participants per
  call, the others once, and all of them for the build as well.
- `campaign.py` can pin glibc's mmap threshold for a whole run, which is every
  participant in it. `pinned-one-thread` and `pinned-full-width` repeat the two
  protocol-size runs with it pinned, so what the threshold is worth is measured
  for each participant rather than assumed for one. Pinning one participant and
  not another would compare two allocators, which is B4's error again.
- The campaign records resident agent sessions by name, at any CPU, before,
  during and after every run. It is not a second gate — CPU and containers
  still decide — but the record now says whether a session was there.

## Four things in the record that look like failures

- **Two parity invocations are marked shared, and one was not started.** The
  sightings in both shared ones are `kswapd0` and `kcompactd0` — the kernel
  reclaiming and compacting memory for the run itself, at 2,097,152 and
  4,194,304 nodes, not a second workload. The idle rule does not make that
  distinction and it was not weakened to let a run pass; the cause was removed
  instead, by dropping the page cache before the timed campaign, and the one
  invocation the rule refused to start (`dockerd` still at 13% of a CPU from
  the previous container's teardown) was rerun afterwards on a quiet host. It
  is the last parity invocation in `campaign.jsonl` and it is clean. Parity
  verdicts are computed results and do not depend on host load; the files are
  the output of the last invocation of each set and configuration.
- **Three parity invocations exited 1.** The protocol fixture set at each
  concurrency: `parity.py` exits 1 whenever a row mismatches, and that set
  always contains the four `neo4j-graph` dangling-mass rows B3 reported. The
  driver takes its verdict from the file, not the exit code.
- **`xlarge-one-thread` reports 129 steal ticks.** 1.3 seconds of steal over a
  4,300-second run, on a host advertised as not burstable. Every cell of that
  run carries its own steal in `tables.md`, and the two `hub-4194304` cells
  carry 121 of the 129; the `uniform-4194304` cells carry 8.
- **One cell is unusable.** `grust-next@counted` PageRank on `path-65536`,
  first call, in `pinned-full-width`, at a MAD above a quarter of its median.
  It is marked in `tables.md` and enters no table — and it is in the same
  family and configuration as the largest regression B5 found, which is stated
  in the results document rather than left to this note.

**No timed run was discarded, and no timed run was rerun.** All eight ran once,
in order, on an idle host, from 07:32:20Z to 09:59:10Z on 2026-09-22. One agent
session was resident on the host throughout — a `codex` session, asleep, using
no CPU — and it is recorded by name in every snapshot in `campaign.jsonl`
rather than left to be reconstructed. Nothing else was started on the host
while a run was in progress: B4's one discarded run was caused by the agent
driving the campaign collecting provenance during it, so here the audit, the
image receipt and the fixture manifest were all taken before parity began.
