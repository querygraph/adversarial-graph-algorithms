# B6, one commit under B5's protocol — quegee, 2026-09-22

What produced these files, so a reader can tell what they are evidence of.

## Why there is a B6

B5 timed Grust `ca68900` and found PageRank on the `path` family at full width
up to 2.2 times v0.22.0, and WCC's first call at one worker 10 to 14% slower,
with the page-fault counter ruling out the allocator state for both. An
attribution on this host, outside the harness, found the first was false
sharing: each work meter's balance was a bare `Arc<AtomicUsize>` in a 32-byte
heap chunk that glibc's tcache placed beside the pool's bookkeeping, which
other cores write. Grust `55a200f` pads the balance to a whole cache line and
was merged to `main` as `87fc462`. B6 times `87fc462` under exactly B5's
protocol, so the two campaigns differ in one thing.

manifest were taken before parity began, not during a timed run.

Host: quegee, 16 vCPU on 8 physical cores, 24.8 MB L3, not burstable.

## What did not change since B5

- **The harness.** `633ff36` differs from B5's `9ec8548` by `b5_report.py`
  alone, which the image copies and nothing in it runs. `plan.json` is the
  output of `campaign.py plan` from this checkout; the same command from B5's
  checkout on the host printed the same bytes (SHA-256
  `d6b1f2b3c01c9c34d7c0536d2ffd147fb12c8aa841f57216837b8891e4a0053b` for both),
  checked before the build.
- **The fixtures.** The twelve files were hardlinked from B5's work directory
  and every SHA-256 and byte count was checked against
  `b5-quegee/fixtures-manifest.json` before the build; `fixtures-manifest.json`
  here records the same check again (`identical_to_b5`).
- **The protocol.** Parity first, every fixture set at concurrency unset, 1
  and 16, with the bits gate of `grust-next` against v0.22.0; the page cache
  dropped after parity and before the first timed run; the eight timed runs in
  B5's order, one warmup and five repeats, idle-checked before and after and
  sampled once a second during; the pinned probe rows; the large and xlarge
  sizes.
- **The v0.22.0 baseline.** `grust` is the same commit as in B3, B4 and B5.

## Things in the record that look like failures

- **Three parity invocations exited 1.** The protocol fixture set at each
  concurrency: `parity.py` exits 1 whenever a row mismatches, and that set
  always contains the four `neo4j-graph` dangling-mass rows B3 reported. The
  driver takes its verdict from the file, not the exit code. Unlike B5, no
  parity invocation was marked shared and none was refused; all nine ran once,
  in order, clean.
- **Every participant is slower above L3 than it was in B5**, by 1.2 to 2.2
  times at 2,097,152 and 4,194,304 nodes, including `icecat`, `grustcat` and
  `neo4j-graph`, which contain no Grust; at the protocol sizes the same
  binaries' sources are within a few per cent of B5, except `icebug` (+60 to
  +103%) and v0.22.0's pull kernel at 65,536 (+18 to +30%, with a MAD ten
  times B5's). The page-fault counts are the same to within a few, steal is at
  most 21 ticks in 5,132 s, and the watcher saw nothing. **The cause is not
  established.** It is why the large and xlarge kernel-change ratios are read
  within B6 only. The cheapest test of the first candidate, transparent
  hugepage starvation, was run beside the control below: `thp_fault_fallback`
  in `/proc/vmstat` did not move across a large run, so it is not that.
- **A control run after the campaign, and its first attempt was discarded.**
  To learn whether the slower host state outlived the campaign, the shortest
  large run, `large-full-width`, was repeated under the same driver with its
  own tag. The first attempt was discarded by the rule: a `du -sh
  /home/admin/src`, not started by this driver, used 10 to 25% of a CPU
  during its last fifteen seconds, eight sightings, all of that one process.
  It is kept as `control/large-full-width-control.discarded.json` and enters
  no table. The second attempt, run with nothing polling the host, was clean:
  0 sightings, 4 steal ticks over 812.6 s, and every participant within a few
  per cent of the campaign's own `large-full-width` cells, so the slower
  state was still there forty minutes after the campaign ended. Both attempts
  are in `control/campaign-control.jsonl`; `control/vmstat-thp.txt` holds the
  `thp_fault_alloc` and `thp_fault_fallback` counters read on both sides of
  each attempt.
- **The `xlarge-one-thread` run took 5,132 s against B5's 4,300 s**, and
  `large-one-thread` 2,334 s against 1,674 s, for the reason above.
- **The B6 campaign ran later in the day than B5's**, 15:10:29Z to 18:07:22Z
  against 07:32:20Z to 09:59:10Z, after the image build, parity and B5's own
  campaign had all run on the host. Nothing in the record ties the slower
  state to that; it is stated because it is the only difference in the host's
  day that the record shows.

**No campaign run was discarded, and no campaign run was rerun.** All eight
ran once, in order, on an idle host. The one agent session resident on the
host throughout, a `codex` session asleep and using no CPU, is recorded by
name in every snapshot in `campaign.jsonl`. Nothing was started on the host by
the agent driving the campaign while a run was in progress: the driver was
polled once every fifteen minutes with a single `grep`, and the audit, image
receipt and manifest were taken before parity began.

## The B5 bundle
